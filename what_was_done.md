# Что за задача и что было сделано

Этот документ объясняет решение в `finance_xakaton.ipynb` простыми словами. Если какой-то биржевой термин непонятен, его можно посмотреть в `about_data__aa.md` или `insample_data/about_data.md`.

## 1. Суть задачи

Нам дали данные Московской биржи в виде parquet-файлов. Это уже не сырой поток заявок и сделок, а заранее посчитанные признаки по времени:

- цены;
- объёмы сделок;
- best bid / best ask;
- размеры заявок в стакане;
- признаки ликвидности;
- признаки волатильности.

Цель хакатона: сделать не просто модель, которая угадывает движение цены, а полный торговый pipeline:

```text
данные -> торговый сигнал -> backtest -> модель импакта -> исполнение заявки -> pnl_net
```

То есть нужно показать полный путь торгового решения:

1. Поняли рынок по данным.
2. Сгенерировали сигнал: покупать, продавать или ничего не делать.
3. Проверили сигнал на истории.
4. Учли, что реальные сделки двигают рынок против нас.
5. Разбили крупную заявку на части и посчитали итоговую прибыль/убыток после издержек.

## 2. Главные требования из формального ТЗ

В `formal_task_hackaton.md` уточнили архитектуру:

| Требование | Что это значит |
| --- | --- |
| Сигнал на 5-мин барах | Решение покупать/продавать принимается не каждую минуту, а по 5-мин агрегатам. |
| Исполнение на 1-мин барах | После сигнала объём сделки разбивается на 1-мин слайсы внутри 5-мин бара. |
| Основная сессия 10:00-18:30 | Берём только основное торговое время. |
| M2 output: `signal_5min` | Таблица сигналов по тикерам и 5-мин барам. |
| M3 output: `backtest_baseline` | Проверка сигнала без стоимости исполнения, через `pnl_mid`. |
| M4 output: `impact_model` | Таблица 1-мин рыночных объёмов и коэффициента импакта `a(t)`. |
| M5 output: `execution_schedule`, `execution_summary` | Расписание исполнения, implementation shortfall и `pnl_net`. |

Главная идея:

```text
5 минут = уровень принятия решения
1 минута = уровень исполнения решения
```

## 3. Какие данные используются

В данных есть две папки:

| Папка | Для чего используется |
| --- | --- |
| `insample_data/is_features_5_min_hackaton` | Для сигнала и baseline backtest. |
| `insample_data/is_features_1_min_hackaton` | Для модели импакта и исполнения внутри 5-мин бара. |

Почему так:

- на 5-мин данных мы решаем, какие инструменты покупать/продавать;
- на 1-мин данных мы решаем, как аккуратно исполнить объём сделки.

## 4. Что реализовано в коде

Основной формальный pipeline находится в:

```text

```

В ноутбуке используется:

```python
result.execution_summary
result.metrics
```

## 5. M2: торговый сигнал `signal_5min`

M2 строит сигнал на 5-мин барах.

Выход:

| Поле | Что означает |
| --- | --- |
| `bar_end_ts` | Время конца 5-мин бара. |
| `seccode` | Тикер инструмента. |
| `value` | Сила сигнала от `-1` до `1`. |

Интерпретация `value`:

| Значение | Смысл |
| --- | --- |
| ближе к `1` | хотим купить / long |
| около `0` | ничего не делать |
| ближе к `-1` | хотим продать / short |

Сигнал сделан как понятный baseline, а не как сложная нейросеть. Он использует:

- дисбаланс агрессивных покупок и продаж;
- дисбаланс объёмов в стакане;
- EMA-сглаживание этих признаков;
- краткосрочный EMA-тренд;
- относительный spread;
- волатильность.

Пример логики:

```text
если покупатели активнее продавцов и в стакане сильная bid-сторона,
то сигнал становится более положительным
```

## 6. M3: baseline backtest `backtest_baseline`

Backtest отвечает на вопрос:

```text
Если бы мы торговали по этому сигналу в прошлом, что бы получилось?
```

Важный момент: сигнал применяется со сдвигом.

```text
сигнал на баре t -> позиция на баре t+1
```

Это нужно, чтобы не использовать будущую информацию.

Выход:

| Поле | Что означает |
| --- | --- |
| `bar_end_ts` | Конец 5-мин бара. |
| `seccode` | Тикер. |
| `pos` | Позиция: сколько стратегии держит в инструменте. |
| `pnl_mid` | Прибыль/убыток без учёта импакта. |
| `cum_pnl_mid` | Накопленный `pnl_mid`. |

`pnl_mid` - это идеализированная прибыль. Она показывает качество сигнала, но ещё не учитывает реальные издержки торговли.

Позиции нормируются long/short: длинная и короткая стороны получают сопоставимый рублёвый вес. Это приближает backtest к требованию портфельной нейтральности из ТЗ.

## 7. M4: модель импакта `impact_model`

Импакт - это влияние нашей заявки на рынок.

Простая идея:

```text
если купить маленький объём, цена почти не изменится
если купить большой объём, придётся забирать всё более дорогие заявки
```

Формальная модель из ТЗ:

```text
cost(x) = a(t) * x
```

где:

- `x` = participation rate;
- `participation_rate = q_slice / volume_mkt`;
- `q_slice` - наш объём в 1-мин слайсе;
- `volume_mkt` - рыночный объём за эту минуту;
- `a(t)` - коэффициент импакта.

Выход:

| Поле | Что означает |
| --- | --- |
| `bar_end_ts` | Конец 1-мин бара. |
| `seccode` | Тикер. |
| `volume_mkt` | Рыночный объём за минуту. |
| `a` | Коэффициент импакта. |

В решении `a` берётся около `0.03` и немного меняется с волатильностью, оставаясь в диапазоне из ТЗ.

## 8. M5: оптимизация исполнения

После сигнала мы не исполняем всю заявку сразу. Мы разбиваем её на 1-мин слайсы.

Например:

```text
есть 5-мин бар
внутри него 5 минут
значит есть 5 слайсов исполнения
```

Нужно распределить объём так, чтобы снизить impact.

В решении используется идея:

```text
больше исполняем в минуты, где больше рыночный объём и ниже impact coefficient
```

При этом есть ограничение:

```text
participation_rate <= x_max
```

В ноутбуке `x_max = 0.30`, то есть мы стараемся не занимать больше 30% рыночного объёма минуты.

## 9. `execution_schedule`

Это детальное расписание исполнения.

Выход:

| Поле | Что означает |
| --- | --- |
| `bar_end_ts_5min` | 5-мин бар, для которого исполняется позиция. |
| `bar_end_ts_1min` | 1-мин слайс исполнения. |
| `seccode` | Тикер. |
| `q_slice` | Сколько исполняем в эту минуту. |
| `participation_rate` | Доля нашего объёма от рыночного объёма минуты. |
| `impact_cost_rel` | Относительная стоимость импакта. |

Это таблица уровня “каждая минута исполнения”.

## 10. `execution_summary`

Это агрегат по исполнению инструмента внутри 5-мин бара.

Выход:

| Поле | Что означает |
| --- | --- |
| `bar_end_ts_5min` | 5-мин бар. |
| `seccode` | Тикер. |
| `Q_executed` | Общий исполненный объём. |
| `vwap_fill` | Средняя цена нашего исполнения. |
| `twap_bench` | Бенчмарк простого равномерного исполнения. |
| `implementation_shortfall` | Стоимость плохого исполнения из-за импакта. |
| `implementation_shortfall_twap` | IS для простого TWAP. |
| `is_reduction` | Насколько наше расписание лучше TWAP по IS. |
| `pnl_mid` | Идеальный PnL без импакта. |
| `pnl_net` | PnL после вычета implementation shortfall. |

Главная формула:

```python
pnl_net = pnl_mid - implementation_shortfall
```

## 11. Что такое `metrics`

В `result.metrics` собраны основные числа для презентации:

| Метрика | Смысл |
| --- | --- |
| `signal_rows` | Сколько строк в таблице сигналов/backtest. |
| `execution_rows` | Сколько агрегированных исполнений посчитано. |
| `pnl_mid_total` | Суммарный PnL без импакта. |
| `pnl_net_total` | Суммарный PnL после импакта. |
| `sharpe_net` | Условная стабильность `pnl_net`. |
| `hit_rate_mid` | Доля баров, где baseline PnL был положительным. |
| `avg_is_reduction` | Среднее улучшение IS относительно TWAP. |

Для защиты особенно важны:

- `pnl_net_total`;
- `avg_is_reduction`;
- график `pnl_mid` vs `pnl_net`;
- таблицы `execution_schedule` и `execution_summary`.

## 12. Как читать `finance_xakaton.ipynb`

Ноутбук устроен так:

1. Импортируется `FormalHackathonPipeline`.
2. Создаётся pipeline с параметрами.
3. Запускается `result = pipeline.run(...)`.
4. Показываются размеры всех формальных выходов.
5. Показывается `signal_5min`.
6. Показывается `backtest_baseline`.
7. Показывается `impact_model`.
8. Показывается `execution_schedule`.
9. Показывается `execution_summary`.
10. Строится график `pnl_mid` против `pnl_net`.
11. Считается статистика по IS и `pnl_net`.

Соответствие по модулям:

| Модуль из ТЗ | Реализация |
| --- | --- |
| M2: сигнал | `result.signal_5min` |
| M3: baseline backtest | `result.backtest_baseline` |
| M4: impact model | `result.impact_model` |
| M5: execution schedule | `result.execution_schedule` |
| M5: execution summary | `result.execution_summary` |
| Метрики | `result.metrics` |

Соответствие по временным масштабам:

| Требование | Реализация |
| --- | --- |
| Сигнал 5 минут | Используется папка `is_features_5_min_hackaton`. |
| Исполнение 1 минута | Используется папка `is_features_1_min_hackaton`. |
| Сессия 10:00-18:30 | Данные фильтруются через `between_time`. |
| `x <= x_max` | В расписании исполнения есть ограничение participation rate. |
| EMA в сигнале | Дисбалансы и краткосрочный тренд сглаживаются через EMA. |
| Universe | Используется фильтр ликвидности `min_avg_volume`, а не фиксированное число тикеров. |
| Нейтральность | Позиции нормируются по long/short сторонам, чтобы приблизить рублёвую нейтральность. |

## 14. Как объяснить это на защите

Короткий вариант:

```text
Мы построили модульный pipeline по формальному ТЗ.
Сигнал строится на 5-минутных признаках стакана и сделок.
Сигнал применяется со сдвигом на следующий бар, чтобы не было заглядывания в будущее.
Baseline считает идеальный pnl_mid без издержек.
Потом на 1-минутных барах строится модель импакта.
Внутри каждого 5-мин бара объём распределяется по 1-мин слайсам с ограничением participation rate.
В конце считаем implementation shortfall и pnl_net.
```

Самый короткий вариант:

```text
Мы не просто предсказываем цену.
Мы показываем весь путь торгового решения:
сигнал -> backtest -> impact -> исполнение -> pnl_net.
```

## 15. Ограничения решения

Это baseline-решение для хакатона, поэтому есть упрощения:

- сигнал rule-based, без сложной ML-модели;
- коэффициент импакта `a(t)` задан и слегка адаптирован через волатильность;
- комиссии явно не моделируются;
- оптимизация исполнения сделана аналитически/эвристически, без тяжёлого оптимизационного solver;
- фильтр universe основан на средней ликвидности, а не на полной задаче оптимального выбора портфеля;
- используется ограниченное число активных баров через `max_execution_bars`, чтобы notebook работал быстрее.

Эти ограничения нормально звучат на защите, потому что основная ценность решения - правильная архитектура pipeline и соответствие формальным выходам M2-M5.
